# Postman API Sync

Use this skill only to generate or update Postman request definitions from the current repository's HTTP API implementation. The local Git-native Postman files are the generated source of truth. Do not use the Postman REST API.

Read [Postman CLI Commands](references/postman-cli.md) before running Postman commands. It records the command sequence, supported flags, and version-dependent fallbacks; check `--help` only when the installed CLI differs or a command fails.

## Safety Rules

- Never run a cloud-mutating Postman command until the user explicitly confirms the selected workspace and proposed changes in the current turn.
- Never use `postman workspace push --push-strategy force-sync`.
- Preserve requests not marked as generated by this skill.
- Do not place secrets, tokens, credentials, or real personal data in Postman collection files.
- Do not invent endpoints, authentication, fields, defaults, or schemas. Mark an endpoint as incomplete and report it when its implementation cannot establish a detail.
- Do not add response examples, response schemas, tests, or mocks unless the user explicitly requests them.

## Preconditions

1. Run `postman --version`. If unavailable, report the missing prerequisite.
2. Check `postman workspace --help` before using version-dependent `workspace list` or `workspace lint`. CLI versions can lack these subcommands.
3. Verify authentication and list workspaces with `postman workspace list --json` when supported. If it is unavailable, use the read-only `postman search workspaces --ownership organization --limit 25 --output json`. If unauthenticated, ask the user to run `postman login` and stop.
4. Determine the service and collection name from the nearest `package.json` name. For a monorepo, ask which service directory to synchronize before changing files.

## Discover APIs

Inspect implementation code, not only README files, tests, or route names. Search all source roots and framework registration points for HTTP routes.

For each endpoint, establish:

- HTTP method and route template.
- Base path/prefix and local-server port when defined by the repository.
- Path parameters, query parameters, repeated-parameter behavior, and requiredness.
- Request headers and content type.
- Authentication scheme and permission requirements.
- Request body media type and exact schema.

Trace request schemas to their definitions. Support the validation/schema mechanism actually used by the repository, including Zod, JSON Schema, TypeBox, Joi, class-validator, framework DTOs, and handwritten runtime validation. Derive field names, scalar types, formats, enums, nested objects, arrays, optional fields, nullability, and constraints only when present in code.

For Azure Functions, inspect each `app.http()` registration, including imported registration modules, then trace `request.params`, `request.query`, `request.headers`, `request.json()`, wrappers, and validators. Include all registered HTTP functions, not only functions imported by the primary entry point when the runtime convention loads them separately.

## Local Collection Layout

Store generated files in the repository:

```
postman/collections/<collection-name>/
.postman/resources.yaml
```

Use Postman's current Git-native collection format. If the repository already has Postman files, preserve its existing format, manifest structure, organization, and cloud-resource mapping.

For a new collection:

1. Create the minimal valid `resources.yaml` with the selected `workspace.id`. A new collection has an empty `cloudResources.collections` map; add a local-path-to-cloud-ID mapping only when updating or renaming a known cloud collection.
2. Create one collection named `<package-name>` unless the user specifies a name.
3. Use `{{<collection-name>-url}}` for the server root unless the repository or user establishes a different shared variable name. Add that collection variable with the local development URL only when it is established from project configuration; otherwise leave it empty and report it.
4. Organize generated requests by the first stable route segment or existing collection folder convention.
5. Add a durable marker to every generated request, for example `x-opencode-generated: postman-api-sync`, using a format accepted by the current Postman collection format.

On an existing collection, identify requests bearing the generated marker. Rebuild only those requests from the current code, retain all unmarked requests unchanged, and remove generated requests only when their endpoint no longer exists. Retain collection-level settings and variables unless this skill owns them.

When using `postman collection migrate`, write directly to the final `postman/collections/<collection-name>` directory. Before any push, inspect the immediate children of `postman/collections/`: it must contain only intended collection directories. The CLI treats stale or empty directories, including those with an empty `.resources/` directory, as separate collections and can create empty cloud collections for them.

## Request Definitions

For every discovered endpoint, generate one request with:

- A human-readable, deterministic name. For existing collections, match their naming convention. When a resource-operation convention exists, use `List <Resource>s`, `Create <Resource>s`, `Get <Resource>`, `Update <Resource>`, or `Delete <Resource>` as applicable. Otherwise use `<METHOD> <route>`.
- The established server-root variable plus the route template (`{{<collection-name>-url}}` by default).
- Path and query parameters represented as Postman URL variables/parameters, with descriptions and requiredness derived from code.
- Required headers and an accurate `Content-Type` for body-bearing requests.
- An authentication configuration only when the implementation identifies a supported scheme. Otherwise add a request description naming the required auth mechanism without fabricating credential values.
- A JSON request body example generated from the schema. Populate required primitives with clearly synthetic valid values; omit optional properties by default; include one representative value for required array elements; use enum values from the code.
- A concise description recording the code-derived validation constraints that Postman cannot represent structurally.

Do not send any generated request. Do not create a request body for methods/endpoints whose code does not consume one.

## Validate And Sync

Before a cloud mutation:

1. Show the selected workspace, collection name, changed generated requests, preserved manual request count, skipped/incomplete endpoints, and files to be changed.
2. Ask for explicit confirmation to write local files. Write only after confirmation.
3. Run `postman workspace prepare` and `postman workspace lint` from the repository root. If `workspace lint` is unavailable in the installed CLI, run `postman collection lint "postman/collections/<collection-name>"` and state the substitution. Fix only generated-file errors; report pre-existing or manual-file errors without altering them.
4. Show the exact `postman workspace push --yes` command and ask for separate explicit confirmation before executing it.
5. On confirmation, run `postman workspace push --yes`. This creates a collection when no mapping exists and updates the mapped cloud collection otherwise.
6. Report the collection ID/link if returned, created/updated request counts, preserved manual requests, and any skipped endpoints.

If the workspace contains a same-named collection but no local cloud-resource mapping, stop and ask whether to link/update that collection or create a distinct collection. Never rely on non-interactive name-conflict resolution for this decision.

To rename a cloud collection, first map the renamed local path to its existing cloud collection ID in `cloudResources.collections`; then seek cloud-sync confirmation. Without this mapping, `postman workspace push --yes` creates a new collection instead of renaming the existing one. If an unintended cloud collection is created, do not use the Postman REST API to delete it; report its ID/link and request manual cleanup.

## Completion

State that Postman files were generated or synchronized, list changed paths, and distinguish local-file validation from successful cloud sync. If Postman reports an error, include the failing command and error summary without exposing credentials.
